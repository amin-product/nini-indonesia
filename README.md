# 二、Online 版目标

当前项目需要从：

**单文件离线旅行工具**

升级为：

# PWA + 离线缓存 + 联网增强

最终希望用户通过 HTTPS 地址访问赤道小尼，并可以添加到手机主屏幕，以接近独立 App 的方式使用。

运行原则：

### 有网

核心旅行内容正常使用，同时自动获取需要的实时数据，并支持外部在线能力。

### 没网

已经缓存的核心旅行内容仍然可以正常打开和使用。

整体定位是：

**离线核心 + 联网增强**

而不是一个必须联网才能运行的网站。

# 三、第一阶段只验证两个联网功能

这一阶段只做：

## ① 实时汇率

当前已经存在汇率换算页面。

Online 版计划升级为：

**IDR → CNY 实时汇率 + 本地缓存。**

目标逻辑：

### 自动更新

每个自然日最多自动查询一次。

不是每天固定时间后台执行，而是：

用户打开赤道小尼
↓
检查本地保存的汇率更新时间
↓
如果今天已经成功更新过 → 直接使用
↓
如果今天尚未更新 + 当前有网络 → 请求最新汇率
↓
请求成功 → 保存汇率 + 更新时间
↓
当天再次打开不重复自动请求

### 手动更新

汇率页面提供：

**↻ 更新汇率**

用户点击后，可以主动请求最新汇率，不受“每天一次自动更新”的限制。

### 离线兜底

优先级：

**最新联网汇率 → 上次成功缓存汇率 → 当前项目已有离线参考汇率**

因此即使完全没有网络，汇率计算也不能失效。

页面后续需要能够让用户知道：

* 当前汇率值
* 最近更新时间
* 当前使用的是联网数据、缓存数据还是离线参考值

具体 UI 可以后续确定。

* standalone 显示

* 行程
* 酒店
* 航班基础信息
* 景点攻略
* 食物攻略
* 图片
* 穿搭
* 紧急信息
* 已缓存汇率
* 其他本地功能

请根据当前实际项目结构决定具体缓存策略。

# 七、技术原则

这是一个**仅供两个人旅行期间使用的小型项目**。

优先级：

**稳定性 > 离线可用 > 手机体验 > 实现简单 > 工程复杂度**

如果：

**HTML + CSS + JavaScript + Manifest + Service Worker**

已经能够很好地实现需求，就优先保持这个方案。

不要为了工程化而：

* 强制引入 React/Vue 等框架
* 引入大量 npm 依赖
* 引入后端
* 引入数据库
* 重写已经正常工作的业务逻辑
* 大规模重构现有 UI
